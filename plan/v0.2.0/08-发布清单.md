## 1. 版本与语义

| 项 | 决定 | 依据 |
|---|---|---|
| 版本号 | `0.1.0` → `0.2.0`（minor） | 新增能力（造幕台、游戏化、流式/回放通道、过检可视化），无破坏性数据契约变更：`schemaVersion` 仍为 1，`.lumen.json` 旧文件照常导入 |
| 存储迁移 | `DB_VERSION` 2 → 3，新增 `progress` store（`03 §7.2`），只加不减 | 加性迁移；回滚代价与处置见 §7.2，发布说明必须写 |
| 不做 major 的理由 | 数据契约、导出格式、命令入口三处都不破 | `doc/00 §1`、`00 §2` 的处置列全是「复用 / 新增」 |
| 不做 patch 的理由 | 用户可见的默认入口变了（造幕台取代右栏为默认） | `00 D1` |
| 改哪里 | `package.json` 的 `"version"`（`scripts` 一字不动） | 唯一版本真相；本轮只写文档，改动在 T-1 执行 |
| README 徽标 | `README.md` 第 7 行改 `[v0.2.0](…/releases/tag/v0.2.0)`，描述改「造幕台版本」 | 现有徽标就是这种写法 |
| tag | `v0.2.0`（annotated，`-a -m "LUMEN 0.2.0 — 造幕台"`），与 `v0.1.0` 同构 | README 里的链接形态 |
| 分支 | 只有 `main` 长期存在；`feat/forge` 这类短分支 ≤ 3 天，合完即删；hotfix 从 tag 切 `fix/x`，回合 `main` 后打 `v0.2.1` | 单人/小团队，长期分支只会制造合流债 |
| 产物 | `dist/`、`public/player/`、`harness/out/` 全部不入库 | `.gitignore` 第 2–4 行 |

## 6. 构建与校验命令序列

两个终端：第一个跑校验，第二个提供 preview。

```powershell
# 终端 A（仓库根目录）
pnpm typecheck
pnpm test
pnpm lint:i18n
pnpm build
```

```powershell
# 终端 B：perf / visual / snapshot 都打 preview
pnpm preview
```

```powershell
# 回到终端 A
pnpm e2e
pnpm snapshot
```

产物体积与导出物核对：

```powershell
# 入口 gzip（预算 285.1KB = v0.1.0 的 245.1 + 40）
$entry = (Select-String -Path dist/index.html -Pattern 'assets/(index-[^"]+\.js)').Matches[0].Groups[1].Value
$path  = Join-Path dist "assets/$entry"
$ms    = New-Object System.IO.MemoryStream
$gz    = New-Object System.IO.Compression.GZipStream($ms, [System.IO.Compression.CompressionMode]::Compress, $true)
$bytes = [System.IO.File]::ReadAllBytes($path)
$gz.Write($bytes, 0, $bytes.Length); $gz.Dispose()
"entry=$entry gzip={0}KB budget=285.1KB" -f [math]::Round($ms.Length / 1KB, 1)

# three 是否独立分块（必须存在且不是入口）
Get-ChildItem dist/assets -Filter 'three.module-*.js' | Select-Object Name, @{n='gzip 参考';e={[math]::Round($_.Length/1KB,1)}}

# 导出物体检（先手工导出一次到 harness/out/export/；文件名走默认或自己填）
node scripts/inspect-export.mjs 'harness/out/export/演示-该换一种载体了.html'
```

`inspect-export.mjs` 的 `externalRefs` 必须为空数组，`slides` 必须等于幕数；这是 R-03 的人工复核路径。

冷构建（清掉旧产物，验证不靠缓存）在 T-1 做一次：

```powershell
Remove-Item -Recurse -Force dist, public/player -ErrorAction SilentlyContinue
pnpm build
Test-Path public/player/lumen-player.js   # 必须 True
```

## 7. 回滚方案

### 7.1 代码

| 场景 | 动作 | 注意 |
|---|---|---|
| 已 tag，线上（用户手里）出问题 | `git revert <坏提交>` → 走一次 `v0.2.1` | tag 一经发布不移动、不重建；已发布的 `v0.2.0` 永久指向当时的提交 |
| 只在本地验出问题，未 tag | `git checkout -- .` 或 `git switch main` 丢弃 `feat/forge` | 不产生 revert 噪声 |
| 需要本地复现 v0.1.0 行为 | `git switch --detach v0.1.0` 后 `pnpm install && pnpm build` | 只用于对照，不在这里开发 |

回滚后必须重跑 `07 §9` 的前 4 门（typecheck/unit/lint:i18n/build）；e2e 与环境相关，按需补跑。

### 7.2 数据迁移（IndexedDB）

现状：单库 `lumen-deck`、`DB_VERSION = 2`、三个 store（`decks` / `assets` / `settings`，见 `src/persistence/kv.ts`）。降级策略是静默切内存（`storageModeNotice()` 为 `true`），用户观感是「刷新后数据没了」。

`03 §7.2` 已决定新增 `progress` store 并把 `DB_VERSION` 提到 3（只加不减）。因此回滚风险从「有没有迁移」变成「旧代码读新库」：

| 项 | 事实 | 处置 |
|---|---|---|
| 升版方式 | `StoreName` 加 `'progress'`、`STORE_NAMES` 同名字符串、`DB_VERSION` 2→3，`onupgradeneeded` 走既有 `for` 循环 | 加性迁移；既有三个 store 不删不重命名 |
| 旧版读新库 | 0.1.0 用 `indexedDB.open('lumen-deck', 2)` 打开 v3 库会 `VersionError` → 静默降级内存 | 发布说明写明：回滚前先导出 `.lumen.json`；游戏进度丢失属于可接受损失 |
| 回滚入口 | 提供 `?reset=1` 删库重建（`kvDel('progress','forge')` + 三个 store 的同名清理） | 给用户一条可执行的自救路径，避免「刷新后失忆」被当成新 bug |
| 记录结构 | `progress/forge` 单键、`v: 1`、`JSON.stringify ≤ 6144` 字节 | 体积与 03 §7.3 对齐 |
| 回滚后校验 | 打开 `/` → 9 幕示例或既有 deck 可见 → `storageModeNotice()` 为 `false` | 一条命令判生死 |

### 7.3 导出 HTML 的兼容性下限

| 项 | 承诺 |
|---|---|
| 已发布的 0.2.0 导出物 | 自包含（内联播放器内核 + deck JSON），回滚应用不影响它，`file://` 双击仍可播 |
| v0.1.0 导出的 HTML | 同样自包含，不需要 0.2.0 做任何事；它不是「导入」场景 |
| 工程文件 `.lumen.json` | `schemaVersion: 1` 永久可读；`migrate` 只加字段不减字段；0.2.0 写出的文件在 0.1.0 里读会被 `migrate` 判为未知版本 —— 发布说明里要求「跨版本协作先导出独立 HTML」 |
| 播放器内核 | 换机器必须先 `pnpm build:player`；导出空白的第一排查项 |

### 7.4 回滚判定

| 症状 | 先查 | 判定 |
|---|---|---|
| 导出 HTML 空白 | `public/player/lumen-player.js` 是否存在 | 不存在 → 重建，不算回滚 |
| 刷新后回到示例 deck | `console` 里的 `[storage] indexedDB 不可用` | 出现 → 按 7.2 处理，不降版本 |
| 造幕台整体白屏 | `console` 是否 `badJson` 连发 | 是 → 关掉真端点回 mock，可用则只回滚通道 |
| 首屏明显卡顿 | 入口 gzip 与 three 是否被提前拉 | three 进首屏 → 立刻回滚该提交 |

## 9. 发布后 24 小时观察

前提：**没有遥测**（`00 D7`），所以观察项全部是「本地信号 + 用户主动回传」。

| 观察项 | 采集方式 | 阈值 / 判定 | 动作 |
|---|---|---|---|
| 错误 toast 数 | `uiStore.toasts` 里 `kind==='error'` 的会话内计数，写进诊断 JSON | 同一错误码 ≥ 3 例 | 按码定位；坏 JSON 集中 → 查修复环与流式拼装 |
| 诊断 JSON | 用户从设置里导出 `lumen-diagnostics.json`（版本、tier、`storageModeNotice()`、通道 id 与 host、最近 5 条错误码、耗时摘要）`+新建` | 能导出即算可用 | 没有它就没有观察，属于 v0.2.0 必交件 |
| 存储降级 | `storageModeNotice()` 为 `true` 的反馈数 | ≥ 3 例 | 立刻 `v0.2.1` 修 `kv` 或回退数据库版本 |
| 首启完成 | 本地 `settings.onboarded`（不联网，只随诊断 JSON 回传） | 明确报「首启卡住」≥ 2 例 | 查引导与 seed 态焦点 |
| 导出失败 | 用户反馈 + `export` 相关 toast | 任一例可复现 | 先查 `public/player/` 是否为旧内核 |
